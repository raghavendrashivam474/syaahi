# UX-07.M1 — Post-Merge Hotfixes

**Type:** Bug-fix microsprint
**Parent:** UX-07 (Onboarding & First-Time User Experience)
**Trigger:** Runtime crashes discovered during manual browser testing after the UX-07 merge to `main` (commit `48ee559`, tag `v-UX-07`)
**Status:** All critical bugs resolved

## Context

UX-07 was merged to `main` with all six workstreams complete: onboarding flow, walkthrough overlay, discovery screen, feed help button, first-time state management, and documentation. Static analysis (`flutter analyze`) reported zero issues. The codebase was clean, tests passed (59 total), and the feature branches were deleted.

Then we opened the app in the browser.

## Bug 1: The Walkthrough Crash (7+ attempts, 2 architectural rewrites)

### The Symptom

Tapping the **?** help button on the feed screen triggered an immediate crash:

```
BoxConstraints forces an infinite width.
The offending constraints were:
  BoxConstraints(w=Infinity, 44.0<=h<=Infinity)
The relevant error-causing widget was: ElevatedButton
```

The render tree showed: `ElevatedButton ← Row ← Column ← ... ← Dialog`. The `Row` was giving its children unbounded horizontal space, and the `ElevatedButton` was demanding infinite width. These two constraints are mathematically incompatible.

### Attempt 1 — Transparent Dialog

The walkthrough was originally built as a `Dialog` widget. The first version used `backgroundColor: Colors.transparent` to get a floating card effect. On the dark theme (`midnightBase` background), this made the dialog completely invisible. You could see the scrim darken but no content appeared.

**Result:** No crash, but no visible UI. Unusable.

### Attempt 2 — Opaque Dialog Background

Changed the dialog background to `SyaahiColors.midnightBase` so the content would be visible against the dark theme. This is when the `BoxConstraints(w=Infinity)` crash first appeared. The `ElevatedButton` inside the action `Row` had `minimumSize: Size(double.infinity, 44)` — a common pattern for full-width buttons. Inside a `Dialog` with finite constraints, this sometimes works because the Dialog's internal `Material` widget provides bounded width. But the `Row` broke that chain.

**Result:** Crash. First encounter with the infinite-width assertion.

### Attempt 3 — maxWidth Constraint on Inner Container

Wrapped the dialog's content in a `Container` with `constraints: BoxConstraints(maxWidth: 480)`. The logic was sound in theory: cap the width before the `Row` sees it. In practice, the `Dialog` widget's internal widget tree (it wraps your child in `Material` → `ConstrainedBox` → `DecoratedBox` → ...) consumed the constraint before it reached our `Container`. The `Row` still received unbounded width.

**Result:** Identical crash. The constraint was being swallowed by the Dialog's internal layers.

### Attempt 4 — Replace Dialog with Center + ConstrainedBox + Material

Decided to abandon the `Dialog` widget entirely and manually construct the overlay using `Center` → `ConstrainedBox(maxWidth: 480)` → `Material` → content. Used PowerShell `.Replace()` to swap out the `Dialog(...)` wrapper for the new structure.

**This is where we hit a recurring infrastructure problem:** the `.Replace()` call silently failed. The file on disk used CRLF line endings, but the PowerShell here-string used LF. The string match never fired, so the file was unchanged. We didn't realize this at the time because `.Replace()` returns the original string unchanged when there's no match — no error, no warning.

**Result:** Identical crash. We thought the fix had been applied. It hadn't.

### Attempt 5 — Complete File Rewrite via WriteAllText

Recognizing the `.Replace()` problem, we did a full file rewrite using `[System.IO.File]::WriteAllText()`. But the rewrite was constructed by concatenating the "new" top half with what we thought was the "old" bottom half. Due to the confusion from Attempt 4's silent failure, the file ended up containing **both** the `Center/ConstrainedBox` wrapper **and** the original `Dialog` wrapper nested inside each other. The `ElevatedButton` was still inside a `Row` inside a `Dialog`.

**Result:** Identical crash. The file was now more broken than before.

### The Pivot — Abandoning Dialog Entirely

After five failed attempts, the decision was made to scrap the Dialog approach completely and rebuild the walkthrough as a `showModalBottomSheet`. The reasoning: bottom sheets are constrained to the screen width by default, which should eliminate the unbounded-width problem at the source. The user explicitly said the Dialog approach was not working and wanted a separate component.

### Attempt 6 — Bottom Sheet Rebuild

Complete file rewrite as `showModalBottomSheet`. Removed `minimumSize: Size(double.infinity, 44)` from the `ElevatedButton`. Added `Expanded` wrappers around both buttons in the `Row`. Removed `isScrollControlled: true` to avoid the `DraggableScrollableSheet` internal wrapper.

**Result:** The user reported the identical crash at the identical line number (147:15) with the identical render tree including `DraggableScrollableNotification`. This meant the file on disk was **still the old version** — the `WriteAllText` call appeared to have succeeded but the content didn't actually change. The exact mechanism of this failure is unclear, but it reinforced the lesson that PowerShell file operations on this codebase are fragile.

### Attempt 7 — Remove isScrollControlled via .Replace()

Tried a targeted `.Replace()` to strip `isScrollControlled: true` from the `showModalBottomSheet` call. Same CRLF mismatch problem as Attempt 4.

**Result:** Silent failure. File unchanged.

### The Breakthrough — Finding the Real Root Cause

At this point, we ran `Select-String` on the walkthrough file searching for `isScrollControlled`, `double.infinity`, and `minimumSize`. **All three returned zero matches.** The file on disk genuinely did not contain any of the crash-causing code.

Yet the crash persisted with the exact same signature: `BoxConstraints(w=Infinity, 44.0<=h<=Infinity)`.

The key insight came from examining the numbers. The height constraint was `44.0` — not an arbitrary value, but the **Material 3 default minimum height for ElevatedButton**. And the width was `Infinity`. This combination (`Size(double.infinity, 44)`) is the default `minimumSize` in Flutter's `ElevatedButtonThemeData` when using Material 3.

**The app's global theme was injecting `minimumSize: Size(double.infinity, 44)` on every `ElevatedButton` in the entire app.** The walkthrough file didn't need to contain this value — it was inherited from the theme. Static analysis (`flutter analyze`) doesn't catch this because it's a runtime layout conflict, not a code error.

### The Fix

One line added to the walkthrough's `ElevatedButton`:

```dart
ElevatedButton(
  style: ElevatedButton.styleFrom(
    minimumSize: const Size(0, 44),  // Override theme's Size(double.infinity, 44)
  ),
  ...
)
```

This overrides the theme's infinite-width minimum for just this one button, allowing the `Row` to size it naturally. The `44` height is preserved to match the rest of the app.

**Result:** Walkthrough bottom sheet slides up cleanly. All five steps navigate correctly. Skip and Get Started both dismiss the sheet. No crashes.

### Why This Took Seven Attempts

1. **The real cause was invisible.** The `minimumSize: Size(double.infinity, 44)` wasn't in the walkthrough file — it was in the theme. Every fix attempt targeted the wrong file.
2. **Static analysis gave false confidence.** `flutter analyze` reported 0 issues throughout. Layout crashes from theme-inherited constraints are invisible to the analyzer.
3. **PowerShell edits silently failed.** At least three of the seven attempts didn't actually modify the file. `.Replace()` with CRLF mismatches returns the original string unchanged, with no error.
4. **The render tree was misread.** The presence of `DraggableScrollableNotification` in the error output was a clue that `isScrollControlled: true` was still active, but we focused on the `ElevatedButton` instead of questioning whether our edits had landed.

## Bug 2: Discovery Screen Back-Navigation Crash

### The Symptom

Pressing the back button on the discovery screen (`/discover`) when it was the first page in the navigation stack (e.g., entered via direct URL) threw:

```
GoError: no routes to pop
```

### Root Cause

The back button called `context.pop()` unconditionally. When the GoRouter stack was empty (direct URL entry, no prior navigation), there was nothing to pop.

### The Fix

```dart
onPressed: () {
  if (context.canPop()) {
    context.pop();
  } else {
    context.go('/welcome');
  }
}
```

Check `canPop()` first. If the stack is empty, navigate to `/welcome` as a safe fallback.

**Result:** Back button works correctly in all navigation scenarios.

## Bug 3: feed_screen.dart Destruction During Merge

### The Symptom

After the UX-07 merge, `feed_screen.dart` was missing the walkthrough import and the help `IconButton`. The file appeared to have been partially overwritten during the merge process.

### Root Cause

The merge involved two feature branches that both touched `feed_screen.dart`. The `-X theirs` merge strategy resolved conflicts by taking the incoming version wholesale, which lost the help button additions from the other branch.

### The Fix

Restored the known-good version from the `v-UX-07` tag:

```powershell
git checkout v-UX-07 -- lib/features/poems/presentation/feed_screen.dart
```

Then manually re-added the walkthrough import and help `IconButton`.

**Result:** Feed screen displays correctly with the **?** help button in the top right.

## Infrastructure Lesson: PowerShell File Editing

Throughout this microsprint, we encountered a recurring problem with editing Dart files via PowerShell:

- **`.Replace()` with multi-line strings** silently fails when the file uses CRLF (`\r\n`) but the PowerShell here-string uses LF (`\n`). The match never fires, the original string is returned unchanged, and no error is thrown.
- **`Set-Content` with here-strings** can corrupt file encoding or strip line endings.
- **The only reliable method** is complete file rewrites via `[System.IO.File]::WriteAllText($path, $content, [System.Text.UTF8Encoding]::new($false))`, which writes UTF-8 without BOM and preserves whatever line endings are in the string.

This caused at least three of the seven walkthrough fix attempts to silently fail, significantly extending the debugging timeline.

## Recommendations for Future Sprints

1. **When a layout crash involves `double.infinity`, search the theme first.** Run `Select-String` across the entire `lib/` tree for the offending value. The cause is often in `app_theme.dart` or a shared `ButtonStyle`, not in the crashing widget.
2. **Never use `.Replace()` for multi-line Dart edits in PowerShell.** Always use `WriteAllText` for complete rewrites.
3. **Always verify edits landed** with `Select-String` or `Get-Content` before testing. Silent failures are the most expensive kind.
4. **Test with hot restart (R), not hot reload (r)** after structural widget changes. Hot reload can preserve stale widget trees.
5. **`Row` + `double.infinity` in `minimumSize` is always fatal.** If any button in a `Row` inherits an infinite-width minimum from the theme, it will crash. Override it explicitlye it?
